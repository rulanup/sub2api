# 用户风险评分与分级输入审核设计

## 背景

当前项目已经支持两类输入审核：

- `ContentModerationService` 调用 OpenAI 兼容的 `/v1/moderations` 接口，默认模型为 `omni-moderation-latest`。
- `securityaudit` 提示词审计支持越狱、非暴力违法、个人敏感信息等风险分类。

现有审核主要由全局/分组配置决定，无法利用用户历史行为区分相同文本的不同意图。例如“如何获取 Cookie？”可能来自浏览器安全学习，也可能来自长期发送窃取凭据请求的用户。新增用户风险评分，用于决定是否把当前输入交给 AI 审核，同时保留本地高置信度硬阻断。

## 目标

1. 为每个用户维护 0–100 的风险分和风险等级，并在管理员用户列表中显示。
2. 根据用户风险分和当前输入的本地风险信号，决定是否调用 OpenAI Moderation API/提示词审计节点。
3. 对高置信度的攻击或违法操作意图，在任何外部 AI 调用和上游调用之前直接拦截。
4. 审计节点超时或不可用时不阻断正常请求，但向管理员暴露结构化告警和运行态指标。
5. 评分不保存原始输入，不因一次模糊命中永久锁定用户，也不直接替代账号封禁策略。

## 推荐方案

### 1. 评分模型

新增独立的 `user_risk_profiles` 数据表，避免频繁更新 `users` 主表造成行锁竞争。每个用户一行，保存：

- `user_id`：用户主键。
- `score`：当前风险分，范围 0–100。
- `level`：`low`、`medium`、`high`、`critical`。
- `last_event_at`：最近一次风险事件时间。
- `last_decay_at`：最近一次衰减计算时间。
- `last_reason_code`：最近一次脱敏原因码。
- `version`、`created_at`、`updated_at`：并发更新和审计字段。

分数使用指数衰减，默认半衰期 24 小时；读取或写入时按经过时间计算当前分，避免后台定时扫描所有用户。评分事件使用原子 SQL 更新，保证同一用户的并发请求不会丢分。

默认等级：

| 分数 | 等级 | 默认审核行为 |
| ---: | --- | --- |
| 0–29 | low | 本地规则通过后不调用外部 AI |
| 30–59 | medium | 调用 OpenAI Moderation API |
| 60–84 | high | 调用 OpenAI Moderation API；启用提示词审计时追加语义审计 |
| 85–100 | critical | 调用全部可用审核层；当前输入命中高置信度本地规则时直接拦截 |

评分只决定审核强度，不单独因为历史分数阻断一条当前请求，避免用户在风险分衰减前被永久误伤。管理员可以在后续版本中增加显式复核或重置入口，但不属于本次最小交付。

### 2. 风险事件权重

评分来源只使用结构化结果，不保存原始提示词：

- 本地高置信度网络安全策略命中：+40 至 +60。
- 外部提示词审计 `block`：+35。
- OpenAI Moderation API flagged：+20 至 +30，按最高类别和分数选择。
- `cyber_policy` 或重复攻击类命中：+30。
- 关键词/滥用检测命中：+10 至 +20。
- 连续多个窗口无风险审核结果：按衰减规则自然下降，不额外设置“清零”跳变。

重复事件通过时间窗口和相同原因码合并，避免单个请求的多条内部路径重复加分。

### 3. 审核路由

所有已有安全审核入口统一经过以下顺序：

```text
请求解析
  → 本地输入归一化与高置信度硬规则
  → 读取/衰减用户风险分
  → 低风险且无当前风险信号：跳过外部 AI 审核
  → medium/high/critical 或当前输入有风险信号：调用已有审核层
  → 根据结果更新风险分
  → 只有允许结果才进入账号选择、计费和上游转发
```

本地规则覆盖：越狱/破限、DDoS/流量攻击、破解卡密、网站入侵、Cookie/会话窃取、钓鱼页面、勒索软件、绕过 API 限流等明确操作意图。规则进行 Unicode、大小写、空白和常见混淆归一化，并要求动作与目标形成高置信度组合；普通安全教育、合规防御和授权测试说明不因单个词命中而拦截。

当前输入有本地风险信号时，即使用户风险分很低，也要进入 AI 审核；这样可以兼顾“普通用户的模糊问题少打扰”和“恶意用户的上下文交给模型判断”。

### 4. OpenAI Moderation API

复用现有 `ContentModerationService`，不新增第二套 OpenAI Moderation 客户端：

- 继续使用管理员配置的 Base URL、API Key、模型、代理、超时和分组范围。
- 当审核路由判定需要 AI 时调用 `/v1/moderations`。
- `pre_block` 的 flagged 结果在上游前返回统一网络安全策略错误。
- `observe` 结果只记录并更新评分，不拦截。
- API 超时、5xx、无效响应只产生管理员可见告警和运行态计数；按已确认策略放行正常请求，不把外部节点故障误判成用户风险。

### 5. 管理员界面

用户管理表新增：

- 风险分数列，显示数值和颜色等级。
- 风险等级列，支持按等级筛选/排序。
- 最近命中原因和时间的简短脱敏摘要。

评分详情不显示原始提示词，只显示原因码、类别、计数和时间窗口；原始输入继续遵循现有审核日志的脱敏与权限控制。

风控/提示词审计运行态新增“审核节点不可用但请求已放行”的告警状态，至少显示最近时间、累计次数和受影响审核层，方便管理员修复配置或节点。

## 错误处理与安全边界

- 本地硬阻断返回统一错误码 `network_security_policy_violation`，客户端消息为“请求被网络安全策略拦截”。
- 硬阻断发生在账号选择、计费预扣、重试和上游 HTTP/WebSocket 建连之前。
- 不把原始输入、Cookie、Token、API Key 或命中的完整片段写入风险评分表和运行日志。
- 审计服务不可用不增加用户风险分，不触发封禁，也不阻断正常请求。
- 用户风险分不是唯一封禁依据；现有内容审核自动封禁和管理员操作保持独立。

## 测试范围

- 风险分的原子加分、上限、指数衰减、并发更新和等级边界。
- 同一用户相同事件去重，避免 HTTP/WS 多阶段重复加分。
- 每个高风险类别至少有命中和安全语境不命中测试。
- 低风险用户跳过 AI，高风险用户调用 OpenAI Moderation API，当前输入有风险信号时低风险用户也进入 AI。
- OpenAI Moderation API flagged 在上游前拦截，且上游调用计数为零。
- 审计节点不可用时请求放行、管理员运行态出现告警、用户风险分不增加。
- 管理员用户列表正确返回和展示风险分、等级与脱敏最近原因。

## 非目标

- 本次不实现基于风险分的自动永久封禁。
- 本次不把风险分暴露给普通用户或 API 客户端。
- 本次不重构现有 OpenAI Moderation API 和提示词审计存储结构之外的无关网关链路。
